# BrightSign API verification

Reference documentation reviewed on 26 November 2026. Signatures below are document-verified. Physical XD236 execution is pending.

## XD236 and BrightSignOS

XD236 is a Series 6 XD6 player in the Cobra firmware family. BrightSign lists **9.1.173** for XD236 among its non-beta downloads. It is the bench reference baseline. The application logs the installed build on each unit. Minimum workable firmware and actual installed versions are pending. Use the same version on A, B and C. The SD package contains no firmware. [BrightSignOS downloads](https://docs.brightsign.biz/releases/brightsignos-releases) · [9.1 release notes](https://docs.brightsign.biz/releases/91) · [XD6 hardware](https://docs.brightsign.biz/hardware/xd6-xd236-xd1036) · [Series 6 feature matrix](https://docs.brightsign.biz/hardware/series-6-feature-matrix)

## Management bridge for the next milestone

BrightSign documents `CreateObject("roNodeJs", filename, {message_port: port, arguments: [...]})`, flat `PostJsMessage(data As AssociativeArray) As Boolean`, and JavaScript `new (require("@brightsign/messageport"))()` with `addEventListener("bsmessage", callback)` and `PostBSMessage(Object message)`. Messages from Node appear as `roNodeJsEvent` where `GetData().reason` is `"message"` and `GetData().message` holds the payload. Keep messages flat and versioned. Bench-test both directions, child termination, path mapping, offline HTTP binding and filesystem behaviour before committing to the CMS runtime. [roNodeJs](https://docs.brightsign.biz/develop/ronodejs) · [messageport](https://docs.brightsign.biz/develop/messageport) · [HTML to Node migration](https://docs.brightsign.biz/technical/html-to-node-migration)

## 0.1.1 content-card calls

`roVideoMode.SetGraphicsZOrder(order As String) As Boolean` places the holding graphic behind the hardware video. `GetResX() As Integer` and `GetResY() As Integer` size an `roImageWidget` using the current graphics plane. The widget uses `SetDefaultMode(mode As Integer) As Boolean`, `DisplayFile(image_filename As String) As Boolean` and `Show() As Boolean`. The image is resized during card preparation. [roVideoMode](https://docs.brightsign.biz/develop/rovideomode) · [roImageWidget](https://docs.brightsign.biz/develop/roimagewidget) · [Image limits](https://docs.brightsign.biz/technical/image-formats)

The video player's audio control interface exposes `SetPcmAudioOutputs(outputs As Dynamic) As Boolean` and `SetVolume(volume As Dynamic) As Boolean`. Player A uses `CreateObject("roAudioOutput", "hdmi")` and followers use integer volume 0. Audio routing and holding-image display remain hardware checks. ## 0.1.2 static IP and display schedule

On `eth0`, the application stages `SetIP4Address(ip As String) As Boolean`, `SetIP4Netmask(netmask As String) As Boolean` and `SetIP4Broadcast(broadcast As String) As Boolean`, then calls `Apply() As Boolean`. It confirms `dhcp`, `ip4_address` and `ip4_netmask` via `GetCurrentConfig()` before persisting the commissioning marker. The card writes an offline network setup result. [Network configuration](https://docs.brightsign.biz/develop/ronetworkconfiguration)

BrightSign's `AEST` time-zone option includes Australian eastern daylight saving. The cards call `roSystemTime.SetTimeZone("AEST")` when needed. Leader scheduling uses `IsValid()` and `GetZoneDateTime("AEST")`. PTP remains responsible for the actual video start timestamp. The leader publishes display state via SyncManager; each player uses `roCecInterface.SendRawMessage(packet As roByteArray)` to request Image View On and Active Source, or Standby. Desktop mocks passed for IPv4 staging, rejection paths, and the Sydney schedule boundaries. Static IPv4 application and CEC behaviour on XD236 hardware remain pending. [System time](https://docs.brightsign.biz/develop/rosystemtime) · [HDMI-CEC](https://docs.brightsign.biz/develop/rocecinterface)

### Player A bench result · BrightSignOS 9.1.82

Version 0.1.3 stopped in `ValidConfig` at `config.players.Count()` with a member function error. Version 0.1.4 passed that line using `For Each` and indexed lookup. Player A assigned itself `192.168.1.11`, entered `NATIVE_READY` with PTP domain 15, requested CEC wake, and played its local 4K25 HEVC presentation. The diagnostics screenshot contained the presentation and the firmware reported fixed `3840x2160x50p` output. After a diagnostics time set and reboot, the clock reported `Australia/Sydney` and remained within 18 seconds of the workstation. The configured network time service could not be resolved. CEC display behaviour and three-player frame alignment need physical verification.

### Leader clock web page · 0.1.6

The HTTPS server uses Node's built-in HTTPS and crypto modules. It exchanges flat, correlated messages through `roNodeJs.PostJsMessage()` and `@brightsign/messageport`. The write path uses `roDateTime.FromIsoString(date-time As String) As Boolean` and `roSystemTime.SetUtcDateTime(utc_DateTime As roDateTime) As Boolean`, then reads back `GetUtcDateTime()` and `IsValid()`. BrightScript owns the real-time clock and Sydney display schedule. [roDateTime](https://docs.brightsign.biz/develop/rodatetime) · [roSystemTime](https://docs.brightsign.biz/develop/rosystemtime) · [Message port](https://docs.brightsign.biz/develop/messageport)

On Player A (BrightSignOS 9.1.82, Node 18.18.2), the 0.1.5 clock page served over HTTPS but the firmware's message bridge did not preserve the Boolean return flag in the expected form. Version 0.1.6 uses string flags and passed authenticated clock read and clock set against the live real-time clock. The time read back was within 0.24 seconds of the workstation. The clock update was followed by a media-end event and a fresh native start. The player continued at `3840x2160x50p`. The Sydney daylight-saving conversion cases passed desktop tests.

### Management suite · BrightSignOS 9.1.82

The suite uses `roVideoPlayer.SetRectangle(roRectangle)` for the lower native window, `GetPlaybackPosition()` and `GetDuration()` for decoder telemetry, `SetVolume(Integer)` for native volume, and `AdjustVideoColor(roAssociativeArray)` for native brightness, hue and saturation. Transport still uses `PlayFile()` and `StopClear()`. `roVideoMode.SetMode(String)` applies an HDMI mode and can restart the application. The network time settings use `GetTimeServer()`, `GetTimeServerIntervalSeconds()`, `SetTimeServer(String)`, `SetTimeServerIntervalSeconds(Integer)` and `Apply()`. [Video player](https://docs.brightsign.biz/develop/rovideoplayer) · [Video mode](https://docs.brightsign.biz/develop/rovideomode) · [Network configuration](https://docs.brightsign.biz/develop/ronetworkconfiguration)

Player A served the authenticated console and reported native 4K50 playback. A locally generated AVC MP4 was streamed to the SD library, accepted by native playability checking and played through Preview. Volume, window sizing, blackout and return to the built-in presentation were verified. The PTP listener heard IPv4 multicast domain 0 while the app reported its own configured domain 15. B and C were offline during the check. Resident file transfers, active timing changes and frame alignment require the group test.

The source renderer passes `Url` for SRT to `roVideoPlayer.PlayFile()`. The web renderer creates `roHtmlWidget` with a rectangle and initialization parameters. The upper layer uses a transparent page. Two webpages are composited in one Chromium widget with browser framing rules in force. The initial two-widget path in 0.2.0 triggered a firmware restart during the overlay test. The recovery build leaves external overlay URLs as session settings and uses a single widget for the combined source. [HTML widget](https://docs.brightsign.biz/develop/rohtmlwidget) · [BrightSign SRT support](https://support.brightsign.biz/hc/en-us/community/posts/360038334993-SRT-Secure-Reliable-Transport)

## 0.1.3 combined card startup

The card launcher runs Ethernet setup and optional local diagnostics before calling `Run()` on the separate playback entry point. It records the last startup stage on SD and checks the interpreter's returned compile or runtime status. This uses vendor-documented `SetupDWS(settings As roAssociativeArray) As Boolean` with the `open` password field, digest authentication, `Apply()`, and a persisted `networking/dwse` setting. The password file is operator-supplied and remains outside release artefacts and version control.
