# BrightSign API verification

Reference documentation reviewed on 26 November 2026. Sections below record the API signatures and physical results available for each feature.

## 0.2.13 Three-Player Playback and Updates

All three XD236 players booted the same signed package at `3840x2160x50p`. The leader package came from the GitHub branch through the workstation. Both followers accepted the local signed file. Each console listed the named SD card presentation. The leader distributed the 30-second, 25 fps Sync Test set, and all three devices verified their assigned MP4.

Live playhead requests on B, C and A moved all three native decoders into a new group playback cycle at 45, 95 and 150 seconds respectively. The leader estimated relative decoder spread of 44, 20 and 36 ms from the reports. These figures describe decoder positions and include report timing variation. HDMI output frame alignment requires a separate measurement. The group jump uses a native `roSyncManager.Synchronize()` timestamp and derives the file's media origin with `roDateTime.SubtractMilliseconds()` before passing it to `roVideoPlayer.PlayFile()`. [BrightSign Video Wall Sync](https://docs.brightsign.biz/technical/video-wall-sync-architecture) · [Video Player](https://docs.brightsign.biz/develop/rovideoplayer) · [roDateTime](https://docs.brightsign.biz/develop/rodatetime)

Playback continued on all three with the display schedule requesting standby after 21:00 Sydney time. The operator confirmed that the TCL on Player A responded to CEC Standby. The Samsung Frame on Player B stayed on. The leader disabled Player B's HDMI audio independently and restored it after readback. All three report HDMI audio enabled and the Australian NTP pool configured. The players reported a name resolution failure on the tested network. [Samsung Anynet+](https://www.samsung.com/au/support/tv-audio-video/what-is-anynet-plus/)

## 0.2.5 Playback, Display and Updates

Player A at `3840x2160x50p` reported native positions of 79,000 ms, 80,360 ms and 81,360 ms in successive console samples. [BrightSign Video Player](https://docs.brightsign.biz/develop/rovideoplayer)

HDMI continued to report On after the Standby request, so physical Standby remains unconfirmed. The schedule flag saved and read back while the existing wake and standby times were preserved. [BrightSign Video Mode](https://docs.brightsign.biz/develop/rovideomode) · [HDMI-CEC](https://docs.brightsign.biz/develop/rocecinterface)

Player A staged version 0.2.6 from the GitHub branch through the workstation. Player B staged the same signed payload from a local file. Desktop tests covered signature rejection, simulated restart failure, atomic slot activation and rollback. ## Management bridge for the next milestone

BrightSign documents `CreateObject("roNodeJs", filename, {message_port: port, arguments: [...]})`, flat `PostJsMessage(data As AssociativeArray) As Boolean`, and JavaScript `new (require("@brightsign/messageport"))()` with `addEventListener("bsmessage", callback)` and `PostBSMessage(Object message)`. Messages from Node appear as `roNodeJsEvent` where `GetData().reason` is `"message"` and `GetData().message` holds the payload. Keep messages flat and versioned. Bench-test both directions, child termination, path mapping, offline HTTP binding and filesystem behaviour before committing to the CMS runtime. ## 0.1.2 static IP and display schedule

On `eth0`, the application stages `SetIP4Address(ip As String) As Boolean`, `SetIP4Netmask(netmask As String) As Boolean` and `SetIP4Broadcast(broadcast As String) As Boolean`, then calls `Apply() As Boolean`. It confirms `dhcp`, `ip4_address` and `ip4_netmask` via `GetCurrentConfig()` before persisting the commissioning marker. The card writes an offline network setup result. [Network configuration](https://docs.brightsign.biz/develop/ronetworkconfiguration)

BrightSign's `AEST` time-zone option includes Australian eastern daylight saving. The cards call `roSystemTime.SetTimeZone("AEST")` when needed. Leader scheduling uses `IsValid()` and `GetZoneDateTime("AEST")`. PTP remains responsible for the actual video start timestamp. The leader publishes display state via SyncManager; each player uses `roCecInterface.SendRawMessage(packet As roByteArray)` to request Image View On and Active Source, or Standby. Desktop mocks passed for IPv4 staging, rejection paths, and the Sydney schedule boundaries. Static IPv4 application and CEC behaviour on XD236 hardware remain pending. [System time](https://docs.brightsign.biz/develop/rosystemtime) · [HDMI-CEC](https://docs.brightsign.biz/develop/rocecinterface)

## 0.1.3 combined card startup

The card launcher runs Ethernet setup and optional local diagnostics before calling `Run()` on the separate playback entry point. It records the last startup stage on SD and checks the interpreter's returned compile or runtime status. This uses vendor-documented `SetupDWS(settings As roAssociativeArray) As Boolean` with the `open` password field, digest authentication, `Apply()`, and a persisted `networking/dwse` setting. The password file is operator-supplied and remains outside release artefacts and version control. ## 0.2.15–0.2.16 console diagnostics

`roVideoMode.Screenshot(parameters As roAssociativeArray) As Boolean` captures the combined video and graphics output. The app requests a 160 × 90 JPEG for each player preview. The IDENT card uses a local `roHtmlWidget` and `Raise()` to display the player configuration without changing the decoder. The HDMI status uses `GetHdmiOutputStatus()` and `GetEdidIdentity(true)` for the attached screen’s name, manufacturer, product and serial when present. [Video mode](https://docs.brightsign.biz/develop/rovideomode) · [HTML widget](https://docs.brightsign.biz/develop/rohtmlwidget)

On XD236 with BrightSignOS 9.1.82, Player A returned a 960 × 540 IDENT capture during playback and a 160 × 90 thumbnail. The output reported the attached TCL, CPU counters and available system RAM. The BrightSign temperature call returned no sensor on this unit. The console also checks the Linux thermal zone interface where the image exposes it. GPU utilisation is unavailable without a verified counter. [Linux thermal sensors](https://docs.kernel.org/driver-api/thermal/sysfs-api.html)

Ethernet configuration uses `SetDHCP()` or `SetIP4Address()`, `SetIP4Netmask()`, `SetIP4Broadcast()`, `SetIP4Gateway()` and `SetDNSServers()` with `Apply()`. The app checks the new profile with `GetCurrentConfig()`. For a grouped player, the configured peer IP must still match. The bench test read the active network profile. A DHCP or static transition requires a separate hardware check. [BrightSign network configuration](https://docs.brightsign.biz/develop/ronetworkconfiguration)

Opt-in CEC remote input uses `roCecInterface.SetPort()`, `GetLogicalAddress()` and the CEC receive event’s `GetByteArray()`. The player accepts directed Play, Pause and Stop keys from the TV. Delivery of TV remote keys on the installation displays remains to be verified. [HDMI CEC object](https://docs.brightsign.biz/develop/rocecinterface) · [Linux CEC command definitions](https://github.com/torvalds/linux/blob/master/include/uapi/linux/cec.h)

All three XD236 units ran the signed 0.2.16 slot and returned to the saved Sync Test revision. Player B saved a 2 × 2 layout and all three consoles reported the same layout. The original 1 × 3 layout was restored. All nine console-to-preview checks returned 160 × 90 JPEGs. HDMI EDID identified a TCL display on A, Samsung on B and a Blackmagic HDMI sink on C. All three reported CPU, memory and SD data. No temperature or GPU utilisation readings were available. Each static Ethernet profile reported zero DNS servers.

Player C played a workstation-generated H.264 feed using native `roVideoPlayer.PlayFile({Url: ...})` against a local RTSP server. The playback API showed the saved source name and the native startup selection reported RTSP. The saved source listing omitted its URL. [BrightSign video player](https://docs.brightsign.biz/develop/rovideoplayer)

Player B displayed the local 0.2.18 colour bars with its name at the upper right. The captured pixels included the expected red and blue patches. The native decoder continued to play the group video while the pattern was visible.
